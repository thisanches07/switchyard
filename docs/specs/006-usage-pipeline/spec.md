# Spec 006: Usage event pipeline

- **Status:** Approved (2026-10-13)
- **Owner:** @thisanches07
- **Release:** v0.1
- **Depends on:** 004
- **Related ADRs:** 0007 (Kafka usage events, idempotent consumer), 0008 (no retry after first byte), 0010 (no prompt persistence), 0011 (OpenTelemetry)

## Problem
Since specs 004 and 005 the gateway knows *who* calls it and limits *how fast*, but it keeps no record of *what was used*. Operators cannot answer "how many tokens did team X use this week", "which model costs us the most" or "did this request really happen". Budgets (spec 007), routing by cost and latency (spec 008), cache savings (spec 009) and the PII and observability work all need the same per-request record, and each of them would otherwise invent its own completion path.

Writing that record to Postgres inside the request would add latency to every call and make the gateway's availability depend on an analytical write (ADR-0007). Switchyard therefore needs:
- **one usage event per admitted request**, produced at a **single request-outcome point** that later specs extend instead of duplicating;
- a **versioned, validated event schema** (`UsageEvent` v1) that already contains the fields later specs fill, so the topic version never changes during v0.1–v0.3;
- **asynchronous delivery** to Kafka (Redpanda locally) through a **bounded** in-memory buffer that never blocks or fails a user request, and that counts what it drops;
- a separate **worker process** that stores events **idempotently** and keeps **daily aggregates** consistent even when Kafka redelivers;
- an **admin endpoint** to read usage back, grouped by team, key, model, provider or day;
- **metadata only**: no prompt or response content ever enters an event (ADR-0010).

## User stories
- As an **operator**, I want every request recorded with tokens, latency, status and who sent it, so I can see and explain usage per team, key and model.
- As an **operator**, I want the gateway to keep serving at full speed when Kafka is down, and to know exactly how many events were lost if the outage lasts too long.
- As an **operator**, I want redelivered or replayed events never to double-count usage, so the numbers stay trustworthy after a worker crash or a replay.
- As an **operator**, I want malformed events set aside in a dead-letter topic instead of blocking the pipeline.
- As a **developer of specs 007–015**, I want one outcome hook and a fixed event schema, so I add a field value rather than a new completion path or a new topic version.
- As a **security reviewer**, I want proof that events contain metadata only.

## Concepts
- **Admitted request:** an authenticated `/v1/chat/completions` or `/v1/embeddings` request that passed model resolution, the allowed-models check and admission (rate limits from spec 005; budgets from spec 007). Requests rejected before admission (`400`, `401`, `403`, `404`, `429`, admission `503`) and `GET /v1/models` produce **no** event; they are visible in metrics and logs only.
- **Request outcome:** how an admitted request ended, recorded exactly once:
  - `success`: the full response was delivered (for streams, `[DONE]` was sent);
  - `upstream_error`: the request failed before any response byte reached the client (provider error or timeout, or any other unplanned gateway-side failure after admission);
  - `upstream_error_midstream`: a stream failed after its first chunk was sent (ADR-0008);
  - `client_closed`: the client disconnected before the response was complete;
  - `rejected`: the request was admitted, then refused by a gateway policy before any upstream call (e.g. PII `block` from spec 010); `provider` and `servedModel` are `null`, tokens are `0`.
- **Outcome hook:** the single point in the proxy module where the outcome is recorded: the non-streaming settle path, and the stream's end, failure and disconnect paths. It runs for every admitted request whether or not usage publishing is enabled, because later specs (budget counters in 007, attempts in 008, cache status in 009, PII counts in 010) attach their own work and data to it.
- **`UsageEvent` v1:** the event contract below, identical to `docs/specs/waves.md`. Fields owned by a later spec are emitted with their default until that spec lands.

| Field | Type | Meaning / default |
|---|---|---|
| `id` | UUIDv7 | Unique event id, generated by the gateway |
| `schemaVersion` | `1` | |
| `occurredAt` | ISO-8601 UTC | When the outcome was recorded (the end of the request); the UTC day and month of this value decide the `usage_daily` row and the budget period (spec 007) |
| `requestId` | string | Same value as the `x-switchyard-request-id` response header |
| `teamId`, `keyId` | UUID | From the authenticated principal |

## Acceptance criteria (EARS)

### Event schema
- **AC-1** THE `UsageEvent` v1 schema SHALL be defined once in core as a Zod schema with exactly the fields, types and defaults in the table above, and SHALL reject unknown fields, a `schemaVersion` other than `1`, an `id` that is not a UUIDv7, negative token counts and a `costUsd` that is not a plain decimal string (no exponent) or `null`. The gateway SHALL validate every event against it before publishing, and the worker SHALL validate every message against it before storing.
- **AC-2** THE event SHALL carry metadata only: no field SHALL contain prompt, message, input, response, tool-call or embedding content, nor key material, and a test SHALL send a request containing a unique marker string and assert that the marker appears in neither the published message bytes nor the stored row (ADR-0010). THE threat model's *Repudiation* row SHALL be updated: events are insert-only (no update or delete API), carry the request id returned to the client and are stored effectively once; the residual risk (events dropped during a long broker outage, counted in metrics) SHALL be stated.

### Outcome hook
- **AC-3** WHEN an admitted request ends, THE gateway SHALL record **exactly one** event, for each of these cases, chat and embeddings, streaming and non-streaming:
  - success → `outcome: "success"`, `status` = the response status (`200`);
  - upstream failure before the first byte → `outcome: "upstream_error"`, `status` and `errorCode` = the error returned to the client (e.g. `502` `upstream_error`, `504` `upstream_timeout`);
  - stream failure after the first chunk → `outcome: "upstream_error_midstream"`, `status: 200` (headers were already sent), `errorCode` = the code of the SSE error event, token counts covering what was streamed (`estimated: true` when not provider-reported);
  - client disconnect → `outcome: "client_closed"`, `status: 200` if response headers were already sent, else `499`, tokens counting what was generated so far;
  - admitted, then refused by a gateway policy before any upstream call → `outcome: "rejected"`, `status` and `errorCode` = the `4xx` error returned, `provider`/`servedModel` `null`, tokens `0` (no policy produces this in 006; the value exists so spec 010 can use it, and a unit test SHALL cover it through the hook).

  In every case `cachedInputTokens` SHALL be the provider-reported prompt-cache read tokens when the provider reports them (OpenAI-compatible: `usage.prompt_tokens_details.cached_tokens`), else `0`. No admitted request SHALL produce zero or two events, and no request rejected before admission SHALL produce one. The outcome hook SHALL run whether `usage.enabled` is `true` or `false`; WHEN it is `false`, THE gateway SHALL build the event but SHALL NOT connect to Kafka or publish it.

### Producer
- **AC-4** THE config file SHALL accept `usage.enabled` (default `true`), `usage.topic` (default `usage.events.v1`), `usage.dlqTopic` (default `usage.events.dlq`), `usage.bufferSize` (positive integer, default `10000`) and `usage.flushIntervalMs` (positive integer, default `200`), and the environment SHALL accept `KAFKA_BROKERS` (comma-separated `host:port` list). IF `KAFKA_BROKERS` is not set, THEN the worker, and the gateway when `usage.enabled` is `true`, SHALL refuse to start with a configuration error naming the variable.
- **AC-5** WHEN an event is recorded, THE gateway SHALL append it to an in-memory buffer and return without waiting for Kafka; the buffer SHALL be published to `usage.topic` with the **team id as the message key** at least every `usage.flushIntervalMs`. Publishing SHALL NOT add latency to, delay, or change the status of any client response.
- **AC-6** IF the buffer already holds `usage.bufferSize` events (e.g. the broker is unreachable), THEN THE gateway SHALL drop the new event, increment `switchyard_usage_events_dropped_total{reason="buffer_full"}` and log a warning at most once per minute; WHEN the broker becomes reachable again, buffered events SHALL be published without a restart. The gateway SHALL start and serve requests while Kafka is down, and `/readyz` SHALL keep returning `200` when Kafka is unreachable (events are best-effort, ADR-0007); the producer's state is observable through the AC-12 metrics.
- **AC-7** WHEN the gateway receives `SIGTERM`, THE producer SHALL publish the buffered events (including those of requests that finish during shutdown) before exiting, within `SHUTDOWN_TIMEOUT_MS`; events still unpublished at the deadline SHALL be counted in `switchyard_usage_events_dropped_total{reason="shutdown"}`.

### Worker
- **AC-8** THE repository SHALL provide a separate worker process (`pnpm dev:worker` in development, its own container in Compose) that consumes `usage.topic` in the consumer group `switchyard-usage-worker`, inserts each valid event into `usage_events` (one row per event, every field of the schema persisted, `cost_usd` as an exact decimal, not a float) and updates `usage_daily` (`day` = UTC date of `occurredAt`, keyed by `day`, `team_id`, `key_id`, `model`; `model` = the served `provider/servedModel` reference, or `requestedModel` when no upstream was called), both created by migration `0002_usage_events`. On a fresh stack, both topics SHALL exist after `docker compose up` without manual steps.
- **AC-9** WHEN the same event (same `id`) is consumed more than once, THE worker SHALL store exactly one `usage_events` row and count it exactly once in `usage_daily` (`requests`, `input_tokens`, `output_tokens`, `cost_usd`, `unknown_cost_requests`): the daily aggregate SHALL be updated only when the insert actually created a row, in the same database transaction. Offsets SHALL be committed only after that transaction commits, so a worker killed mid-batch and restarted loses no event and double-counts none.
- **AC-10** IF a message is not valid JSON or fails the AC-1 schema, THEN THE worker SHALL publish the original bytes to `usage.dlqTopic` with headers giving the reason and the source partition and offset, commit past it and keep consuming. IF Postgres is unavailable, THEN the worker SHALL NOT send messages to the DLQ nor commit their offsets; it SHALL pause and retry with backoff until Postgres is back. `cost_usd` in `usage_daily` SHALL sum only known costs, and events with `costUsd: null` SHALL increment `unknown_cost_requests` instead.

### Reading usage
- **AC-11** `GET /admin/usage` (admin token, spec 004) SHALL accept:
  - `from`, `to`: UTC dates `YYYY-MM-DD`, both inclusive; defaults `to` = today (UTC) and `from` = `to` minus 29 days; at most 366 days apart;
  - `groupBy`: `team` · `key` · `model` · `provider` · `day` (default `day`);
  - optional `teamId` and `keyId` filters.

  It SHALL respond `200` with `{ "from", "to", "groupBy", "data": [ { "group", "requests", "inputTokens", "outputTokens", "costUsd", "unknownCostRequests" } ], "totals": { "requests", "inputTokens", "outputTokens", "costUsd", "unknownCostRequests" } }`, where `group` is the team id, key id, model reference, provider name (`null` for requests that reached no provider) or date, `costUsd` is a decimal string summing known costs only (`"0"` when none are known), `data` is sorted by date ascending for `day` and by `costUsd` then `requests` descending otherwise. Malformed dates or ids, `from` after `to`, a range over 366 days or an unknown `groupBy` SHALL return `400` `invalid_request`. The route SHALL appear in the OpenAPI document. Results are eventually consistent: in the Compose stack an event SHALL be visible within 10 s of its request completing.

### Observability
- **AC-12** THE gateway SHALL export `switchyard_usage_events_dropped_total{reason}`, `switchyard_usage_events_published_total` and a `switchyard_usage_buffer_events` gauge (current buffer length); the worker SHALL export `switchyard_usage_worker_events_total{result="inserted"|"duplicate"|"dlq"}` and create a `switchyard.usage.consume` span per batch (message count, result counts; no event content). Neither process SHALL log event fields other than ids, model, provider, outcome and counts.

### Tests and smoke
- **AC-13** Integration tests SHALL run the producer and the worker against a real Redpanda and Postgres (Testcontainers) and prove: publish → stored row and aggregate; the same event published twice → one row and aggregates counted once; a malformed message → DLQ while the next valid one is stored; worker restart mid-stream → no loss and no double count; broker down → buffer fills, drops are counted, delivery resumes when the broker returns.
- **AC-14** THE Compose stack SHALL include the worker service, and the Compose smoke test SHALL make a chat request with a key created through the admin API and then observe that request counted in `GET /admin/usage?groupBy=key` within 10 s.

## Non-goals
- Cost calculation and budgets: `costUsd` stays `null` until spec 007.
- Billing-grade delivery: no on-disk outbox; prolonged broker outages lose events, counted (ADR-0007).
- Opt-in content logging (ADR-0010) and any storage of prompt or response content.
- Retention, partitioning or archival of `usage_events`; re-aggregating `usage_daily` from scratch.
- Hourly or finer-grained aggregates, dashboards (spec 011) and usage export formats (CSV, Parquet).
- Usage endpoints for non-admin callers (a key reading its own usage).
- Events for requests rejected before admission.

## Open questions
- Should `/readyz` mention Kafka at all? (Proposed: report `"kafka": "ok" | "degraded"` in the `checks` object from the producer's own connection state, with no extra network round trip, and never list it in `failing` or turn the status to `503`; if that complicates the readiness contract, leave Kafka out of `/readyz` entirely and rely on the AC-12 metrics.)
- Which outcome describes a gateway-side failure after admission that is neither a provider error nor a policy refusal (e.g. `provider_not_configured`, an internal error)? (Proposed: `upstream_error` with the real `errorCode`, keeping `rejected` for deliberate `4xx` policy refusals; revisit if specs 008–009 need a separate `gateway_error`.)
- What `status` does a non-streaming `client_closed` event carry, since no response was sent? (Proposed: `499`, the de-facto "client closed request" code; streams whose headers were sent keep `200`.)
- Should `occurredAt` be the request start or its end? (Proposed: the end, when the outcome is known; a request that spans UTC midnight is counted on the day, and in the budget month, in which it finished. `latencyMs` gives the start if needed.)
- `usage_daily` has no `provider` column in the shared contract. How is `groupBy=provider` answered? (Proposed: `usage_daily.model` holds the served `provider/model` reference, so the provider is its prefix; rows for requests that reached no provider use the requested model and are grouped under `null`. Alternative: answer `groupBy=provider` from `usage_events`.)
- Strict schema validation means an older worker sends events with a new optional field to the DLQ. (Proposed: keep it strict, since it also guards against content slipping into events; deploy the worker before the gateway whenever a field is added, and replay the DLQ if the order was wrong.)
- Should a DLQ replay command ship with this spec? (Proposed: no; document how to re-publish with `rpk`, and add a command only if DLQ traffic shows up in practice.)
