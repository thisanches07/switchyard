# Spec 014: Anthropic provider adapter and Messages API

- **Status:** Approved (2026-10-13)
- **Owner:** @thisanches07
- **Release:** stretch (implemented in wave A)
- **Depends on:** 003, 004, 005
- **Related ADRs:** 0003 (OpenAI-compatible API), 0004 (canonical format + adapters), 0008 (no retry after first byte), 0010 (no content in logs), 0011 (OpenTelemetry), 0016 (Anthropic Messages compatibility surface)

## Problem
The example config routes the `smart` alias to `claude/claude-sonnet-5-5`, but the `anthropic` provider type is still a placeholder that answers `501 provider_not_implemented` (spec 002). Any alias with a Claude candidate is therefore broken, and operators who pay for Claude cannot use it through the gateway.

The other half of the problem is inbound. A growing share of client code (agent frameworks, coding tools, anything written against the official Anthropic SDKs) speaks the Anthropic Messages API, not the OpenAI one. Those clients cannot use Switchyard at all today, so their traffic bypasses the gateway's keys, limits, telemetry and (soon) usage accounting, budgets and PII redaction.

The two APIs differ in ways a naive proxy gets wrong: the system prompt is a top-level field, `max_tokens` is mandatory, tool calls are content blocks rather than a side array, tool results are user-side blocks rather than a `tool` role, streaming uses named SSE events with typed deltas and no `[DONE]`, usage separates cache reads and writes, and errors have a different shape and an extra `529 overloaded_error` status. This spec makes each of those translations explicit and tested, in both directions, without needing a paid key in CI.

## User stories
- As an **operator**, I want `claude/...` candidates to work through `/v1/chat/completions` (streaming and tools included), so aliases like `smart` can route to Claude.
- As an **application developer** using the official Anthropic SDK (TypeScript or Python), I want to point its base URL at Switchyard and keep my code unchanged, so my traffic gets the gateway's keys, limits and telemetry.
- As an **application developer** on the Anthropic SDK, I want to reach non-Anthropic models (Groq, Gemini, Ollama, mock) by model name or alias, so I can switch providers without switching SDKs.
- As an **operator**, I want Anthropic failures (overloaded, rate limited, timeouts) classified like any other provider failure, so fallback and circuit breaking (spec 008) treat Claude the same way.
- As a **maintainer**, I want the whole translation layer tested against recorded fixtures and a fake Anthropic server, so CI never needs a paid key.

## Concepts
- **Outbound adapter:** the `anthropic` provider implementation. It receives the canonical (OpenAI-shaped) request (ADR-0004), calls the Anthropic Messages API (`POST {baseUrl}/v1/messages`) and returns canonical responses and chunks.
- **Inbound surface:** the new route `POST /v1/messages`. It accepts an Anthropic Messages request, converts it into the canonical request, routes it like any chat request and converts the result back into an Anthropic `message` or Anthropic SSE events.
- **Same-family path:** inbound `/v1/messages` resolved to an `anthropic` provider. The request still passes through the canonical form, but Anthropic-only data (thinking blocks, `cache_control`, `top_k`, `metadata`, documents) is carried alongside it and re-emitted unchanged (ADR-0016), so nothing is lost.
- **Cross-family path:** inbound `/v1/messages` resolved to a non-Anthropic provider, or `/v1/chat/completions` resolved to an `anthropic` provider. Only what both formats can express survives; the rest is dropped or rejected according to the tables fixed in ADR-0016.
- **Error surface:** the error shape is chosen by the **route the client called**, never by the provider: `/v1/chat/completions` and `/v1/embeddings` keep the OpenAI shape (ADR-0003); `/v1/messages` uses the Anthropic shape (ADR-0016).

## Acceptance criteria (EARS)

### Outbound adapter (`/v1/chat/completions` to an `anthropic` provider)
- **AC-1** WHEN a chat request resolves to a provider of type `anthropic`, THE gateway SHALL call `POST {baseUrl}/v1/messages` (default `baseUrl` `https://api.anthropic.com`) with headers `x-api-key` (from `apiKeyEnv`), `anthropic-version: 2023-06-01` and `content-type: application/json`; IF the key's environment variable is unset, THEN it SHALL answer `503 provider_not_configured` exactly like `openai-compatible` (spec 002). The `501 provider_not_implemented` placeholder SHALL be removed.
- **AC-2** THE adapter SHALL translate the canonical request as follows, verified by unit tests on pure functions: all `system` (and `developer`) messages concatenated, in order, into the top-level `system`; consecutive messages of the same role merged so roles alternate; `max_completion_tokens`, else `max_tokens`, else the provider's `defaultMaxTokens` (new optional field on the `anthropic` provider config, default `4096`) into `max_tokens`; `stop` (string or array) into `stop_sequences`; `temperature`, `top_p` and `user` (as `metadata.user_id`) passed through; `image_url` parts as `image` blocks (`data:` URIs as `base64` sources with their media type, `http(s)` URLs as `url` sources). Parameters Anthropic cannot honour SHALL follow the ADR-0016 table: `n > 1`, `logprobs`/`top_logprobs` and `response_format` other than `text` rejected with `400 unsupported_parameter` naming the parameter; `presence_penalty`, `frequency_penalty`, `seed` and `logit_bias` dropped and listed in the span attribute `switchyard.dropped_params`.
- **AC-3** THE adapter SHALL translate tools both ways: `tools[].function` into `{name, description, input_schema}`; `tool_choice` `auto`/`none`/`required`/`{function:{name}}` into `{type:"auto"}`/`{type:"none"}`/`{type:"any"}`/`{type:"tool",name}`; `parallel_tool_calls: false` into `disable_parallel_tool_use: true`; assistant `tool_calls` into `tool_use` blocks (with `arguments` parsed as JSON; IF they are not valid JSON, THEN `400 invalid_tool_arguments`); consecutive `role: "tool"` messages into a single `user` turn of `tool_result` blocks keyed by `tool_use_id`. In responses, `tool_use` blocks SHALL become `message.tool_calls` (`id`, `type: "function"`, `function.name`, `function.arguments` as a JSON string) and text blocks SHALL be concatenated into `message.content`. Thinking blocks SHALL NOT appear in the OpenAI response. Tool-choice values a model rejects upstream (some current models refuse `any`/`tool`) SHALL surface as the upstream 400, not be pre-validated.
- **AC-4** THE adapter SHALL map `stop_reason` to `finish_reason` as `end_turn`, `stop_sequence`, `pause_turn` → `stop`; `max_tokens`, `model_context_window_exceeded` → `length`; `tool_use` → `tool_calls`; `refusal` → `content_filter`; any unknown value → `stop`. It SHALL report usage as `prompt_tokens = input_tokens + cache_creation_input_tokens + cache_read_input_tokens`, `completion_tokens = output_tokens`, `prompt_tokens_details.cached_tokens = cache_read_input_tokens`, and fill the canonical `Usage` with the same totals (plus the cache-read count, for spec 009).
- **AC-5** WHEN an embeddings request resolves to an `anthropic` provider, THE gateway SHALL answer `400` with `code: "embeddings_not_supported"` naming the provider, without calling upstream.

### Inbound Messages API (`POST /v1/messages`)
- **AC-6** THE gateway SHALL expose `POST /v1/messages` accepting the Anthropic Messages request (`model`, `max_tokens` required; `messages`, `system` as a string or text blocks, `stop_sequences`, `temperature`, `top_p`, `top_k`, `tools`, `tool_choice`, `metadata`, `stream`), validated with Zod and documented in the OpenAPI spec. It SHALL authenticate the gateway key from `x-api-key` **or** `Authorization: Bearer` (if both are present and differ, `401`), and SHALL resolve `model` exactly like chat (alias or `provider/model`, allowed-models check, `x-switchyard-*` headers). The `anthropic-version` request header SHALL be accepted and not required.
- **AC-7** WHEN a `/v1/messages` request resolves to an `anthropic` provider (same-family path), THE upstream request SHALL preserve, byte-for-byte in a fixture comparison with PII mode `off`, the client's content blocks (including `thinking`, `redacted_thinking`, `document` and `cache_control`), `system` blocks, `top_k`, `metadata`, `tools` and `tool_choice`; and the client SHALL receive the upstream content blocks, `stop_reason`, `stop_sequence` and `usage` (including `cache_creation_input_tokens` and `cache_read_input_tokens`) unchanged, with `model` set to the name the client requested and `id` from upstream.
- **AC-8** WHEN a `/v1/messages` request resolves to a non-Anthropic provider (cross-family path), THE gateway SHALL apply the reverse of AC-2 to AC-4 (top-level `system` → `system` message, `tool_result` blocks → `role: "tool"` messages, `tool_use` blocks ↔ `tool_calls`, `finish_reason` → `stop_reason` with `stop` → `end_turn` (or `stop_sequence` with `stop_sequence` set when it matches a requested sequence), `length` → `max_tokens`, `tool_calls` → `tool_use`, `content_filter` → `refusal`) and return an Anthropic `message` with an `id` of the form `msg_…` and `usage.input_tokens`/`output_tokens`. Blocks that have no equivalent SHALL follow the ADR-0016 table: `thinking`/`redacted_thinking` in earlier assistant turns and `cache_control` markers dropped; `document` blocks and server tools (tools with a `type` other than `custom`) answered with `400 invalid_request_error` naming the field; `top_k` passed through (a provider that rejects it answers with its own 400).
- **AC-9** EVERY `/v1/messages` request SHALL pass rate-limit admission (spec 005) with `max_tokens` as the completion allowance, and its responses (success and `429`) SHALL carry `anthropic-ratelimit-requests-{limit,remaining,reset}` and `anthropic-ratelimit-tokens-{limit,remaining,reset}` (reset in RFC 3339) for the most restrictive bucket, plus `retry-after` on `429`; the OpenAI-style `x-ratelimit-*` headers SHALL also be sent. Completed requests SHALL reach the request-outcome hook (spec 006) with `operation: "messages"`, and the request span SHALL carry `gen_ai.operation.name=chat` and `switchyard.api=anthropic`, without content (ADR-0010).

### Streaming
- **AC-10** WHEN `/v1/chat/completions` streams from an `anthropic` provider, THE adapter SHALL translate the named SSE events into `chat.completion.chunk` events: `message_start` → a role chunk (`delta.role: "assistant"`); `content_block_delta`/`text_delta` → `delta.content`; `content_block_start` of a `tool_use` block → `delta.tool_calls[{index, id, type: "function", function: {name, arguments: ""}}]` and each `input_json_delta` → an `arguments` fragment at the same `index`; `message_delta` → the chunk with `finish_reason` (AC-4); `message_stop` → end of stream (`data: [DONE]`). `ping`, thinking and signature deltas and unknown event types SHALL be ignored. Usage SHALL be taken from the last `message_delta` (cumulative) combined with `message_start`, and the final usage chunk SHALL follow spec 003 AC-7 (`stream_options.include_usage`).
- **AC-11** WHEN `/v1/messages` is called with `stream: true`, THE gateway SHALL respond with Anthropic SSE: named events (`event: <type>` + `data: {…, "type": "<type>"}`) in the order `message_start`, then per content block `content_block_start`, one or more `content_block_delta`, `content_block_stop`, then `message_delta` (with `stop_reason` and cumulative `usage.output_tokens`) and `message_stop`, with no `[DONE]`. On the same-family path the upstream events SHALL be forwarded unchanged except `model`; on the cross-family path they SHALL be synthesised from canonical chunks (text deltas as `text_delta`, tool calls as `tool_use` blocks with `input_json_delta`). Chunks SHALL be forwarded without buffering and client disconnects SHALL abort upstream, as in spec 003 AC-2 and AC-6.
- **AC-12** THE gateway SHALL write nothing to the client (headers included) until the first upstream event that produces client-visible output (on `/v1/chat/completions`, thinking blocks do not count); IF Anthropic sends `event: error` or fails before the first byte is written to the client, THEN the failure SHALL follow the pre-first-byte path (spec 003 AC-4: a normal HTTP error, eligible for retry/fallback in spec 008). IF a failure happens after the first byte, THEN the gateway SHALL end the stream with one error event in the shape of the **route** (OpenAI `data: {"error":…}` on `/v1/chat/completions`, `event: error` + `{"type":"error","error":{…}}` on `/v1/messages`), SHALL NOT retry (ADR-0008) and SHALL record `outcome: upstream_error_midstream`.

### Errors
- **AC-13** THE outbound adapter SHALL map Anthropic errors (HTTP status plus `error.type`) into `GatewayError` as follows: `400`, `403`, `404`, `413` and `422` passed through as client errors with the upstream message and `code: "upstream_<status>"` (spec 002 behaviour); `401` → `502 upstream_auth_error` (the operator's key is wrong, not the client's); `429` → `429 upstream_rate_limited` keeping upstream `retry-after`; `529 overloaded_error` → `503 upstream_overloaded`; `500` → `502 upstream_error`; `504 timeout_error` and gateway timeouts → `504 upstream_timeout`. Upstream `429`, `5xx`, `529`, timeouts and network errors SHALL be marked retryable for spec 008; all other `4xx` SHALL NOT. Upstream request ids (`request-id` header) SHALL be recorded as a span attribute, never the error body content.
- **AC-14** EVERY error returned on `/v1/messages` (validation, auth, `403 model_not_allowed`, `404 model_not_found`, `429`, upstream and internal errors) SHALL use the Anthropic shape `{"type":"error","error":{"type","message"},"request_id"}`, with `error.type` chosen by HTTP status (`400` `invalid_request_error`, `401` `authentication_error`, `402` `billing_error`, `403` `permission_error`, `404` `not_found_error`, `413` `request_too_large`, `429` `rate_limit_error`, `503`/`529` `overloaded_error`, `504` `timeout_error`, other `5xx` `api_error`), `request_id` equal to `x-switchyard-request-id`, and a `request-id` response header with the same value. Errors on every other route SHALL keep the OpenAI shape unchanged.

### Tests
- **AC-15** THE outbound adapter SHALL be tested without a paid key: unit tests over recorded Anthropic response and SSE fixtures (text, tool use, mixed text + tool use, thinking blocks, `error` event before and after content, each `stop_reason`), and integration tests against a fake Anthropic HTTP server started in-process that asserts the request headers and body of AC-1 to AC-3 and serves `429`, `529` and `500` responses. An optional live test SHALL run against the real API only when `ANTHROPIC_API_KEY` and `SWITCHYARD_LIVE_ANTHROPIC=1` are set, and be skipped with a clear message otherwise.
- **AC-16** WHEN the contract suites run, THE official Anthropic **TypeScript** and **Python** SDKs (base URL = the gateway origin, gateway key as `apiKey`) SHALL, against the `mock` provider and in CI: create a message, stream one (event iteration and the `finalMessage`/`get_final_message` helper), complete a tool-use round trip (`tool_use` → `tool_result` → final text), and raise `RateLimitError`, `AuthenticationError`, `NotFoundError` and an `InternalServerError` subclass for 429, 401, unknown model and an upstream 5xx (with SDK retries disabled). The same suites SHALL run the same-family path against the fake Anthropic server. The existing OpenAI contract tests SHALL additionally cover a `/v1/chat/completions` call (plain, streamed and with tools) routed to the fake Anthropic server.

## Non-goals
- Other Anthropic endpoints: `/v1/messages/count_tokens`, Message Batches, Files, Models (`GET /v1/models` keeps its OpenAI shape) and the beta namespaces are not provided.
- Exposing thinking/reasoning content through `/v1/chat/completions` (dropped; see Open questions).
- Server-side tools (web search, code execution, computer use, MCP connector) on the cross-family path.
- Anthropic on Amazon Bedrock, Google Cloud or Microsoft Foundry (different auth and URLs); only the first-party API.
- Prompt-caching strategy (adding `cache_control` automatically): the gateway only preserves markers the client sends (AC-7).
- Retries, fallback and circuit breaking themselves (spec 008); this spec only classifies errors.
- Exact tokenisation for Claude models: rate-limit estimates use the spec 005 heuristic and reconcile with the reported usage.

## Open questions
- **Thinking blocks through the OpenAI surface.** Current Claude models (the example alias targets Sonnet 5.5) cannot fully disable thinking, and Anthropic's errors page says a tool-use continuation whose latest assistant turn had its `thinking` blocks removed is rejected with `400`. OpenAI-SDK clients never echo thinking back, so a multi-turn tool loop through `/v1/chat/completions` may fail on those models. (Proposed: drop thinking from OpenAI responses, document the limitation per model, and verify with the manual live test during implementation; if it fails, carry thinking blocks in an opaque, gateway-signed extension field on the assistant message (`switchyard_thinking`) that Switchyard re-inserts, decided in the design with an ADR-0016 amendment. No outbound `thinking` parameter is set by default.)
- **Role alternation.** The API reference summary we read suggests Anthropic now combines consecutive same-role turns itself; this was not confirmed in the full page. (Proposed: merge consecutive same-role messages in the adapter anyway, which is harmless either way.)
- **Where the gateway's own error `code` goes on `/v1/messages`.** The Anthropic shape has no `code`. (Proposed: put it in `error.details.error_code`, mirroring how Anthropic itself reports `enforced_spend_limit_reached`, so SDK users can branch on it without parsing messages.)
- **Status for upstream `529`.** Forwarding `529` keeps Anthropic semantics but is non-standard for OpenAI clients. (Proposed: `503 upstream_overloaded` on `/v1/chat/completions`; on `/v1/messages` same-family path, also `503` with `error.type: "overloaded_error"`, because `503` is retried by both SDK families.)
- **Default `max_tokens`.** Anthropic requires it; OpenAI clients usually omit it. (Proposed: per-provider `defaultMaxTokens`, default `4096`; too low a default truncates answers silently, so `finish_reason: "length"` makes it visible and the docs call it out.)
- **`x-api-key` on `/v1/chat/completions`.** Accepting it everywhere is simpler but widens the OpenAI surface. (Proposed: accept both headers on every `/v1` route, since the key format is the same and the logger already redacts both; the OpenAI error message keeps recommending Bearer.)
- **`anthropic-beta` request header.** Clients may send beta flags. (Proposed: forward it on the same-family path only; ignore it on the cross-family path.)
- **Images by URL on cross-family paths.** Not every OpenAI-compatible provider fetches image URLs. (Proposed: pass them through as `image_url` and let the provider reject; no fetching or re-encoding in the gateway, to avoid SSRF.)
